**我建议：以 ezBookkeeping 为底座做二次开发，保留成熟的日常记账功能，再增加独立的加密资产模块。不要从头重写，也不要把两套完整财务软件拼起来。**

你的产品核心应该是：

> **平时像一木一样记账；需要看资产时，现金、股票、基金和加密货币能放在同一张资产表里。加密资产按实际持有数量，自动更新市值。**

## 4. 技术架构

### 4.1 延续原有技术栈

ezBookkeeping 的现有技术组合包括 Go、Vue、TypeScript、Pinia，以及手机侧的 Framework7、桌面侧的 Vuetify；依赖中已有 ECharts 和 decimal.js。继续使用这些基础，不另起一套前端体系。:chatgpt-content-reference{index="11"}

建议架构：

```text
手机 / 电脑浏览器
        │
        ▼
现有 Vue 前端
日常记账 + 新增投资页面
        │
        ▼
同一个 Go 服务
├── 原有账户、交易、分类服务
├── 投资事件与成本服务
├── 统一资产估值服务
├── 行情适配与缓存服务
└── 导入、备份、后台任务
        │
        ▼
同一个用户数据库
```

**初版使用模块化单体，不拆微服务，不引入消息队列，也不强制增加 Redis。**

### 4.2 必须分清三层数据

**交易事实层：**用户实际做了什么，例如买入数量、实际支付金额、手续费、时间。

**计算结果层：**根据交易事实推算的剩余持仓、剩余成本、已实现损益。

**行情估值层：**外部最新价格、汇率，以及据此计算的当前市值。

这三层不能混在一起。

尤其禁止：

> 行情上涨后，通过自动写入一笔“收入”，或者直接修改账户余额来模拟浮盈。

价格变化只能更新估值，不能改写用户的交易事实。

## 5. 产品交互与页面设计

## 5.1 整体方向

保留“一打开就能记一笔”的轻量体验，不做成交易所界面。

视觉采用安静、清晰的记账工具风格：中性背景、统一强调色、清楚的数字层级。上涨下跌需要同时使用正负号与文字，不能只靠颜色。

手机底部导航建议为：

```text
账单    统计    ＋记账    资产    设置
```

默认进入账单页，不默认进入币价页面。

### 5.2 账单页

顶部显示本月支出、本月收入和结余，下面是按日期分组的流水。

普通消费行优先显示：

```text
午餐
餐饮 · 微信
−28.00
```

投资交易可以出现在完整流水中，但必须标注为“投资买入”“投资卖出”“资产转移”，并允许筛选隐藏。

**月度生活支出不能被一笔买币操作放大。**

### 5.3 记一笔

普通记账优先让用户完成：

```text
输入金额 → 选择分类 → 保存
```

账户使用用户上次选择或已设置的默认值。备注、日期等次要信息放在可展开区域。

保存成功后保留明确反馈，不能因为自动关闭弹窗，让用户不知道是否已经记上。

投资操作放在资产页，不把普通记账页面塞满交易字段。

### 5.4 资产页

顶部优先显示净资产，下面区分日常账户、投资资产和负债。

投资卡片示意，以下数字均为演示数据：

```text
比特币 BTC

持有数量      0.01000000 BTC
当前市值      ¥7,000.00
持仓成本      ¥6,000.00
持仓盈亏      +¥1,000.00

参考价格更新于 10 秒前
```

需要明确区分：

**账户视角：**某交易平台或钱包里有哪些资产。

**币种视角：**我的所有账户合计持有多少 BTC。

两种视角共用同一份底层持仓数据，不能维护两份数量。

### 5.5 首次添加持仓

入口提供两种明确选择：

| 选择 | 适用情况 | 是否扣资金账户余额 |
|---|---|---|
| **录入已有持仓** | 已经买了很久，只想开始追踪 | 不扣 |
| **记录一笔新买入** | 刚发生了一笔实际交易 | 按选择的结算方式扣款 |

录入已有持仓只强制填写：资产、所在账户、当前数量。

成本可以不填。**不知道成本时显示“成本未录入”，不能把成本当作零，然后显示巨额盈利。**

### 5.6 手机与电脑的差异

手机优先使用单列卡片、底部操作面板和大尺寸数字输入；电脑提供列表、筛选和并排信息。

手机不得出现整页横向滚动。常用点击区域按至少约 44 像素设计，数字输入框避免被软键盘遮挡。

这是本项目的设计要求，不是让 AI 按电脑布局机械缩放。

## 6. 账务规则：必须先确定，再写界面

### 6.1 日常消费与资产交换分开

| 行为 | 日常收支统计 | 资产变化 |
|---|---|---|
| 买午饭 | 记生活支出 | 现金类资产减少 |
| 收到工资 | 记生活收入 | 现金类资产增加 |
| 银行卡转入自己的支付账户 | 不算收入或支出 | 资产位置改变 |
| 用资金买 BTC | 不算生活支出 | 资金减少，持仓增加 |
| 卖 BTC | 不把全部卖出款当生活收入 | 持仓减少，资金增加 |
| BTC 涨价 | 不生成收支流水 | 当前估值增加 |
| 自己的钱包之间转币 | 不算收入或支出 | 持仓位置改变，手续费除外 |

投资费用和投资损益在投资模块展示，不混入默认生活消费统计。

### 6.2 成本计算方式

第一版统一使用：

> **按用户、投资账户、资产分别计算的移动加权平均成本。**

这是本产品的个人投资分析口径，不将其包装为税务申报口径。

设：

```text
Q：当前持有数量
C：当前剩余成本，以本位币记录
A：平均单位成本，A = C ÷ Q
```

买入后：

```text
新数量 = 原数量 + 实际到账数量
新成本 = 原成本 + 本次实际取得成本
```

卖出时：

```text
释放成本 = 卖出数量 × 卖出前平均单位成本
已实现净损益 = 本位币净卖出所得 − 释放成本

剩余数量 = 原数量 − 卖出数量
剩余成本 = 原成本 − 释放成本
```

当前持仓：

```text
持仓市值 = 剩余数量 × 当前本位币参考单价
未实现盈亏 = 持仓市值 − 剩余成本
```

全部卖出时，必须释放全部剩余成本，避免舍入后留下无法消除的尾差。

### 6.3 手续费口径

第一版必须支持手续费使用结算货币支付。

例如以 USDT 买 BTC，手续费也以 USDT 支付：

```text
扣除的 USDT = 成交支出 + 手续费
新增 BTC 成本 = 上述扣款按交易时汇率折算的本位币金额
```

卖出手续费从卖出所得中扣除。

已经计入取得成本或净卖出所得的手续费，**不能再次从盈亏里扣一次**。

交易所若从买入资产中扣费，应支持按“实际到账数量＋实际总支出”录入，不能同时重复扣减到账数量。

第三种资产支付手续费的复杂场景，第一版可以明确不支持，但必须在表单中阻止错误录入，不能悄悄假设它与结算货币相同。

### 6.4 USDT、USDC 也按资产处理

不能把稳定币当作固定等于美元的普通现金字段。

本项目中，USDT、USDC 都具有独立数量、价格和成本。

用 USDT 买 BTC 时，应当在同一笔事件中：

```text
减少 USDT 持仓
增加 BTC 持仓
记录交易当时的 USDT → 本位币折算率
```

USDT 被处置时，也要释放它自身的成本。由此产生的折算损益归入投资模块，而不是生活收入。

**没有交易时历史汇率，就要求录入实际折算率，或标记相关盈亏不可计算。不能偷偷拿今天的汇率代替。**

### 6.5 自己的账户之间转移

无手续费时：

```text
转出账户减少数量 q
转入账户增加数量 q
对应历史成本随数量转移
整体数量、整体成本、整体盈亏均不变
```

转入不能当作一笔零成本买入。

同币种网络手续费应另外扣除相应数量。需要展示手续费当时的参考价值，同时移除其对应成本。

内部计算可采用：

```text
手续费资产的处置损益 = 手续费市值 − 对应历史成本
投资费用 = 手续费市值

两项合计对已实现净损益的影响 = −对应历史成本
```

这样与剩余持仓的未实现盈亏合并后，资产变化能对得上，且不会重复扣费。

### 6.6 修改历史交易

持仓必须能由有效事件重新计算，不能只维护一个可直接覆盖的余额。

修改或撤销历史买入后，需要重算其后的成本、卖出损益、转移成本，以及受影响的历史估值。

如果重算导致任何时点持仓为负，拒绝该次修改，并告诉用户哪笔后续交易产生冲突。

## 7. 如何接入原有记账系统

这是本次二次开发中最需要认真处理的部分。

### 7.1 不把币数写进原有金额字段

普通资金账户继续使用原来的金额体系。

加密资产的数量、价格和成本进入新增投资表。不要为了支持 BTC，把全部旧账户金额字段、货币校验和旧报表一次性推倒重做。

### 7.2 法币买卖使用系统结算对手账户

为复用原有转账能力，可以在内部增加按法币区分的**系统投资结算对手账户**。

例如，用银行卡买币：

```text
原有记账层：
银行卡 → 系统投资结算对手账户

新增投资层：
增加 BTC 数量与成本
```

卖出则方向相反。

关键约束：

**系统对手账户不是用户真实资产。** 必须用明确的系统角色标记，在账户选择、总资产、资产图表和正常账户列表中排除。

不能仅靠原来的“隐藏账户”开关来处理，也不能假设“界面隐藏了，就不会计入总资产”。

系统对手账户余额不代表持仓成本，更不代表持仓市值。

### 7.3 同一次操作必须原子提交

买币的一次保存应同时完成：

```text
资金账户变动
投资事件保存
持仓与成本更新
原有流水与投资事件关联
```

全部成功才算成功；任何一步失败，全部回滚。

原项目的 `CreateTransaction` 已经在内部开启数据库事务，因此新增投资服务不能简单连续调用几次现有入口，假设它们天然属于同一个事务。应抽出可复用、接受同一数据库会话的内部写入方法。:chatgpt-content-reference{index="12"}

### 7.4 统一资产汇总

新增统一的估值服务：

```text
净资产 =
真实日常账户的净余额折算
+ 投资持仓的当前市值
+ 其他手动估值资产
```

排除系统对手账户，沿用并正确归一化原系统的负债符号，避免负债被扣两次。

首页、资产页、分布图、历史快照必须调用同一套口径。

与投资事件关联的旧流水，不允许绕过投资服务单独删除或修改；批量修改、导入和旧接口也必须遵守这个限制。

## 8. 数据结构与精度

### 8.1 建议新增的数据实体

以下是逻辑结构，具体文件与表名遵循上游代码习惯。

| 实体 | 核心内容 |
|---|---|
| `investment_settings` | 用户、本位币、会计时区、成本口径 |
| `portfolio_accounts` | 投资账户名称、归属用户、平台或钱包类型 |
| `instruments` | 资产唯一 ID、类型、名称、符号、数量精度 |
| `instrument_provider_mappings` | 资产与不同数据源 ID、交易对的对应关系 |
| `investment_events` | 事件类型、发生时间、版本、有效状态、原始录入事实 |
| `investment_event_legs` | 每笔事件中各资产的流入流出数量、结算信息 |
| `positions` | 可重建的持仓数量、剩余成本、成本完整性状态 |
| `investment_transaction_links` | 投资事件与原有资金流水的关联 |
| `market_quotes` | 最新价格、来源、报价时间、抓取时间、质量状态 |
| `valuation_snapshots` | 历史估值、组成项、使用的报价及汇率 |
| `idempotency_records` | 防重复提交的请求键、请求摘要和处理结果 |
| `import_batches` | 导入来源、映射规则、错误、去重和批次信息 |

汇率历史需要保留；优先检查现有实现能否复用，不够时补充。

交易事实是原始数据。`positions`、成本分配和统计结果属于计算产物，必须可以重建。

### 8.2 资产不能只靠缩写识别

`symbol` 只用于展示，不能作资产唯一标识。

BTC、同名代币、包装资产、不同数据源的 ID，都需要明确映射。涉及链和合约时，要额外记录相应身份信息，不能看到缩写相同就自动合并。

手动创建的私人资产不得意外公开给其他用户。

### 8.3 精度规则

**金额、数量、价格、汇率，在新增接口中全部使用十进制字符串。**

例如：

```json
{
  "quantity": "0.01234567",
  "unitPrice": "650000.123456",
  "fee": "6.50"
}
```

后端建议采用 Go 的高精度十进制库，例如 `shopspring/decimal`；前端沿用已有 `decimal.js`。前者提供任意精度十进制计算能力。:chatgpt-content-reference{index="13"}

本项目要求：

数量、价格、汇率至少支持 18 位小数；中间运算精度至少高于最终结果要求两位，除法精度必须显式设置，不能依赖库的默认值。

人民币通常显示两位小数，但计算过程不要提前四舍五入。

SQLite 中新增高精度字段采用规范化十进制文本，由后端十进制库计算。**不能因为列名写了 DECIMAL，就默认 SQLite 已经提供了精确十进制运算。** PostgreSQL 后续可以使用适当精度的 `NUMERIC`。:chatgpt-content-reference{index="14"}

输入超过支持精度时明确报错，不静默截断。

## 9. 行情方案

### 9.1 定义“实时”

本项目追求的是：

> 页面打开时，支持实时行情的持仓在正常网络情况下约数秒至十余秒更新；不追求交易终端级别的逐笔报价。

同时必须区分：

```text
实时参考报价
延迟参考报价
手动估值
行情过期
暂时无法估值
```

不是所有资产都能获得同样更新频率，界面不能统一写成“实时”。

### 9.2 默认行情组合

**第一层：Coinbase 公共行情流。**

其官方文档提供无需鉴权的市场数据 WebSocket；`ticker_batch` 在价格变化时按约 5 秒批量提供最新报价，适合作为部分主流资产的初版实时来源。:chatgpt-content-reference{index="15"}

```text
wss://ws-feed.exchange.coinbase.com
```

资产映射必须根据实际产品列表建立，不能仅通过拼接 `币种-USD` 猜测交易对存在。官方提供交易对列表接口。:chatgpt-content-reference{index="16"}

**第二层：CoinGecko。**

用于补充资产信息、覆盖未接入实时流的资产，以及提供低频备用报价。

其价格接口支持按唯一资产 ID 批量查询，并返回价格更新时间；Demo 接口应使用对应的域名和鉴权方式。:chatgpt-content-reference{index="17"}

```text
GET https://api.coingecko.com/api/v3/simple/price
Header: x-cg-demo-api-key

参数示例：
ids=bitcoin,ethereum
vs_currencies=usd,cny
include_last_updated_at=true
precision=full
```

**第三层：用户手动估值。**

外部数据无法使用时，用户仍可保存持仓，并手动填价格。手动报价要有自己的来源与日期，不能伪装成自动行情。

### 9.3 免费额度不能忽略

本次查看的 CoinGecko 定价页列出 Demo 每月 10,000 次调用，并要求署名；不同套餐的数据新鲜度、商业许可等条件不同。不能把免费接口当成无限调用、无限再分发的数据源。:chatgpt-content-reference{index="18"}

按一次批量请求计算：

```text
每分钟请求一次，30 天：43,200 次
每 15 分钟请求一次，30 天：2,880 次
```

因此初版采用：

**实时源由服务端维护共享连接；低频源默认每 15 分钟批量更新。** 资产搜索与元数据另外缓存，并设置调用预算。

前端每 10 秒查询自己的服务器缓存，不等于每 10 秒请求一次 CoinGecko。

### 9.4 行情缓存和异常处理

行情模块必须处理断线重连、心跳、乱序消息、超时、限流、数据源切换和无报价资产。

每份报价至少记录：

```text
资产 ID
报价货币
价格
数据来源
源报价时间
本服务收到时间
连接状态 / 价格质量状态
```

不能把“这次读到了缓存”当成“价格刚刚更新”。

价格长时间没有变化与连接断开也要区分；有正常心跳但没有新成交，不应直接判定网络故障。

备用源报价天然更慢，必须标为延迟。缺失价格时不能用零代替。

### 9.5 人民币估值

使用美元行情时：

```text
人民币参考市值 =
持有数量 × 美元参考单价 × 当前 USD/CNY 参考汇率
```

币价更新时间与汇率更新时间分别保存、分别可查看。

历史成本使用交易时确定的折算率，当前市值使用当前估值汇率，二者不能混用。

启动时检查行情源的网络可用性和配置。数据源适用地区、使用条款及公开服务许可需要在实际部署时核实，不能承诺所有服务器都能直接接入。

## 10. 盈亏展示和历史曲线

### 10.1 第一版优先展示这三项

**当前市值、未实现盈亏、已实现净损益。**

成本不完整时，不输出完整盈利数字。汇总页可以显示“已知成本部分的盈亏”，但必须说明覆盖范围。

币价的“24 小时涨跌”可以展示，但标签必须是币价涨跌，不能写成“你今天赚了多少”。

### 10.2 不用资产增加冒充投资收益

新增持仓、追加资金、转入资产都会使市值增加，但不一定产生盈利。

后续增加个人区间收益时，至少需要明确：

```text
区间投资损益 =
期末投资价值
− 期初投资价值
− 区间外部净投入
```

“外部”相对于选定投资组合而言。组合内部转账不算投入；期初录入、数量校准等也要单独处理。

第一版没有把这些情况计算正确之前，宁可不显示个人“今日收益率”。

### 10.3 历史资产曲线

历史资产必须使用当时的数量和当时的价格：

```text
历史市值(t) = 当时持有数量(t) × 当时价格(t)
```

**禁止用今天的持仓数量乘历史币价，伪造过去的资产曲线。**

第一版从开始使用起保存历史估值快照。没有足够历史数据时显示缺口或“自某日开始记录”，不要编造完整历史。

编辑历史交易后，标记相关快照失效并重建；缺少历史行情的时间段保持不可计算。

### 10.4 估值不完整时怎么显示

如果一项资产没有价格：

```text
已估值资产：¥……
另有 1 项资产暂未估值
```

不能把可计算部分直接标为“完整净资产”。

旧报价可以用于标注清楚的参考估值，但必须显示过期状态。

## 11. 接口与一致性要求

原有记账接口继续沿用。新增接口复用原有鉴权和用户隔离。

下面是建议的新接口契约，不代表上游已经存在：

| 接口 | 用途 |
|---|---|
| `GET /api/v1/investments/instruments` | 搜索和选择资产 |
| `GET/POST /api/v1/investments/accounts` | 投资账户 |
| `POST /api/v1/investments/events/preview` | 预览交易对数量、资金、成本的影响 |
| `POST /api/v1/investments/events` | 提交投资事件 |
| `GET /api/v1/investments/events` | 查询投资流水 |
| `POST /api/v1/investments/events/{id}/revise` | 修订事件并重算 |
| `POST /api/v1/investments/events/{id}/void` | 撤销事件并重算 |
| `GET /api/v1/investments/positions` | 当前持仓 |
| `GET /api/v1/investments/quotes` | 获取行情缓存 |
| `GET /api/v1/wealth/summary` | 统一资产汇总 |
| `GET /api/v1/wealth/history` | 历史估值 |

### 防重复与并发

每次新增交易使用客户端生成的 `Idempotency-Key`。

相同用户、相同键、相同内容重试时，返回同一结果，不再记一笔。相同键但内容不同，返回冲突。

修改使用版本号校验。两个设备同时修改同一事件时，不能互相覆盖。

持仓检查、资金变动和保存必须放在同一数据库事务中。不能先查“余额够”，过几秒再保存。

### 用户隔离

所有私人账户、交易、持仓、导入与导出都必须绑定登录用户。

服务端不能相信请求体传来的用户 ID。预览接口、后台重算、批量导出同样要检查归属。

## 12. 从一木迁移与备份

### 12.1 先做通用导入，不虚构专用适配

目前没有提供一木实际导出文件，因此不能假定它的列名、日期格式、转账表达或账户字段。

第一版复用现有导入基础，完成：

```text
上传 CSV
→ 识别编码与表头
→ 用户映射字段
→ 预览
→ 检查错误与重复
→ 确认导入
```

获得真实样本后，再增加“一木导入预设”。

导入至少映射日期、类型、金额、账户、分类和备注。转账要配对，不能把转出和转入误认成支出及收入。

### 12.2 起始余额避免重复

首次迁移必须让用户选择：

**历史流水方式：**使用历史流水及其起始余额重建当前余额。

**当前余额方式：**录入当前余额，从迁移日开始记账。

不能把“当前余额”当作期初余额，再叠加已经包含在这个余额中的全部历史流水。

已有加密资产优先通过期初持仓录入，无须强迫用户补齐多年交易。

### 12.3 导出与恢复

提供两种导出：

**可读业务导出：**日常流水、投资事件、持仓与费用等 CSV。

**完整恢复备份：**数据库、附件、必要元数据、版本信息及校验信息。

完整备份必须包括新增投资表、内部关联和系统结算角色，不能只调用原项目导出接口就宣称备份完整。

恢复必须在空白实例验证一次，并比较恢复前后的余额、数量、成本和净资产。

## 13. 安全、离线与部署

### 13.1 安全底线

沿用已有账户安全能力，默认关闭公开注册，首次创建自己的账户后再投入使用。

密钥留在服务端，不写入前端代码、仓库或日志。日志不记录完整财务数据。

只向行情供应商发送需要查询的资产标识，不发送用户的持仓数量、成本、备注和账户名称。

生产环境必须使用 HTTPS，并限制备份文件访问。**自托管不等于端到端加密，不得宣传未实现的加密能力。**

### 13.2 第一版的离线边界

PWA 可以缓存应用外壳；断网时允许保存本地草稿，并明确显示“尚未同步”。

没有收到服务端成功结果前，不显示“已入账”。

第一版不承诺多设备离线合并。用户退出登录后清理对应的私人缓存，不能让下一位用户看到上一人的数据。

### 13.3 部署要求

先支持一个应用服务加一个持久化数据目录。

开发 AI 应提供可直接运行的：

```bash
docker compose up -d --build
```

同时交付环境配置示例、健康检查、日志查看、备份、恢复和升级说明。

数据目录必须挂载持久化存储；更新镜像不能丢数据。

正式环境与演示环境使用不同数据库。演示价格要显著标记，不能在真实行情失败后偷偷切成模拟价格。

前端资源、字体和图标尽量随应用自托管，不依赖第三方 CDN 才能正常显示。

## 14. 开发顺序

| 阶段 | 工作 | 完成标志 |
|---|---|---|
| **第一阶段：运行底座** | 锁定上游版本，运行原项目，确认记账、账户、导入及双端页面 | 原有功能可正常使用 |
| **第二阶段：账务计算** | 新增资产、事件、数量、成本、期初持仓、买卖与转移 | 核心计算测试通过 |
| **第三阶段：资金关联** | 与原有账户原子结算，完成系统对手账户和统一汇总 | 不重复计资产，不污染生活收支 |
| **第四阶段：真实行情** | 行情适配、缓存、汇率、过期与失败状态 | 至少 BTC、ETH 获得真实参考报价 |
| **第五阶段：产品界面** | 资产页、持仓详情、交易预览、手机与电脑优化 | 完整操作流程可用 |
| **第六阶段：迁移与交付** | 导入、备份恢复、部署、权限和回归测试 | 能作为个人试用版本运行 |

**先做一个完整可用的流程，再扩展币种和图表。**

最小完整流程是：

> 创建账户 → 记日常支出 → 录入已有 BTC → 获取真实价格 → 查看统一资产 → 记录卖出 → 数据重启后仍正确。

不要先做十几个漂亮页面，最后才发现余额和成本无法对上。

## 15. 必须通过的验收测试

### 15.1 固定计算测试

以下全部是人工构造的测试数据，不是实时币价。

初始银行卡余额：**20,000.00 元**。

依次记录：

```text
第一次买入：
0.01 BTC，成交金额 6,000 元，手续费 6 元

第二次买入：
0.01 BTC，成交金额 7,000 元，手续费 7 元
```

正确结果：

| 项目 | 结果 |
|---|---:|
| 银行卡余额 | 6,987.00 元 |
| BTC 数量 | 0.02000000 BTC |
| 持仓总成本 | 13,013.00 元 |
| 平均单位成本 | 650,650.00 元/BTC |

将测试行情设置为 **750,000 元/BTC**：

```text
持仓市值 = 15,000.00 元
未实现盈亏 = 1,987.00 元
净资产 = 21,987.00 元
```

随后卖出 **0.005 BTC**，成交金额 **4,000 元**，手续费 **4 元**：

```text
净卖出所得 = 3,996.00 元
释放成本 = 3,253.25 元
已实现净损益 = 742.75 元

剩余数量 = 0.01500000 BTC
剩余成本 = 9,759.75 元
银行卡余额 = 10,983.00 元
```

将当前测试行情设置为 **800,000 元/BTC**：

```text
剩余持仓市值 = 12,000.00 元
未实现盈亏 = 2,240.25 元

已实现净损益 + 未实现盈亏 = 2,983.00 元
净资产 = 22,983.00 元
```

这组数据必须覆盖后端计算、接口返回和页面显示。

### 15.2 其他关键测试

| 测试 | 必须满足 |
|---|---|
| 普通账户互转 | 净资产不变，生活收入与支出不变 |
| 录入已有持仓 | 不扣银行卡，不产生生活收入 |
| 未填写成本 | 显示成本未知，不能按零成本计算收益 |
| 只更新行情 | 数量、交易、成本均不变 |
| 跨投资账户转币 | 无手续费时，总数量与总成本不变 |
| USDT 买 BTC | 两种持仓正确变化，保留交易时折算率 |
| 手续费 | 不重复扣减成本或盈亏 |
| 重复提交 | 只产生一笔有效事件 |
| 并发卖出 | 不允许超卖 |
| 修订历史买入 | 后续成本与卖出损益同步重算 |
| 行情断网或过期 | 不显示零价格，不伪装刚更新 |
| 用户权限 | 不能查看、修改或导出他人的财务数据 |
| 数据恢复 | 余额、数量、成本和关联与备份前一致 |
| 手机体验 | 无整页横向滚动，输入与保存流程可完成 |

至少使用手机窄屏、普通手机宽度和桌面三种视口做页面验收。
